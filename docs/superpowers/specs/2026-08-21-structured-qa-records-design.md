# 结构化答疑记录设计

## 目标

把“保存聊天全文”升级为“保存一次知识缺口如何被关闭的证据”。原始消息继续保存在
`chat_messages`，每个会话最多有一条可反复更新的结构化 Q&A 记录，用于描述原误解、
正确模型、掌握证据和仍未解决的部分。

## 范围

- 本地 SQLite 持久化结构化记录，刷新、重启和换页面后仍可读取。
- GitHub Pages 使用同一前端 API，在当前浏览器会话内模拟读写。
- 一条记录可以关联一个知识点、错题或课程。
- 答疑页从最近一轮用户问题和 AI 回答预填前两项，用户不必重新抄写。
- 本阶段不自动声称“已经掌握”，掌握证据必须由用户填写，状态必须显式选择。
- 本阶段不自动生成记忆项或任务；结构化记录先成为后续回流的可靠输入。

## 数据模型

新增 `qa_records`，schema 版本提升到 17。

| 字段 | 含义 |
|---|---|
| `id` | 稳定记录 ID |
| `session_id` | 对应聊天会话，唯一 |
| `subject` | 学科 |
| `context_type` / `context_id` | 可选关联；类型为 `knowledge_item`、`question` 或 `lesson` |
| `original_understanding` | 原来的理解、问题或卡点 |
| `corrected_model` | 答疑后形成的正确模型 |
| `mastery_evidence` | 自己复述、独立做对题目等证据 |
| `unresolved` | 仍未解决部分 |
| `status` | `open`、`understood`、`follow_up` |
| `created_at` / `updated_at` | 创建与更新时间 |

`session_id` 必须在 `chat_messages` 中存在。关联对象必须成对提供类型和 ID，并在对应表中存在。
这避免出现只有类型没有目标、或指向已不存在对象的“假关联”。

## API

- `GET /api/chat/records/{sessionID}`：读取；不存在返回 404。
- `PUT /api/chat/records/{sessionID}`：按会话幂等创建或更新。

请求体包含结构化字段，不接收客户端生成的记录 ID。服务端保留首次创建时间，每次写入更新
`updated_at`。会话学科以请求体为准，但必须非空。

## 前端交互

答疑页在存在会话且最近一条 AI 消息完成后显示“整理这次答疑”面板：

1. 面板初次打开时读取已有记录；404 视为尚未整理。
2. 没有已有记录时，用最近一条用户消息预填“原来怎么想”，用最近一条已完成 AI 回答预填“现在的正确模型”。
3. 所有配置单列排列，一行一个字段。
4. “关联对象”是单个选择框，合并当前学科的知识点、错题和课程；不要求用户输入内部 ID。
5. 保存成功后明确显示更新时间；失败保留当前草稿。

为了保持 `Chat.tsx` 可读，表单放在独立的 `QARecordPanel` 组件中。组件只通过 API 边界读写，
不直接操作静态演示状态。

## GitHub Pages

静态适配器保存 `qaRecords` 映射，实现与本地相同的 GET/PUT 语义。关联列表继续复用现有
知识点、错题和课程静态数据，因此 Pages 能完整演示面板，不需要后端。

## 错误处理

- 空会话、空学科、非法状态、类型/ID 不成对：400。
- 会话或关联对象不存在：404。
- 数据库失败：500，前端显示可重试提示并保留草稿。
- 旧数据库由 v17 迁移创建表；新数据库直接从 `schema.sql` 建立完整结构。

## 验证

- 模型与存储测试：校验、创建、更新、关联完整性、重开数据库后仍存在。
- HTTP 测试：GET 404、PUT 创建、PUT 更新、非法关联。
- 前端 API 与静态适配器测试：路径、请求体和 Pages 会话内持久化。
- 组件测试：预填、读取已有记录、关联选择、保存、错误保留。
- Chat 页面测试：只有完成的会话才出现结构化面板。
